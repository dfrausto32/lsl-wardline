# Windows tunnel and installer hosting (task 2.0)

Decided by Dylan on 2026-10-28.

## Decision 1: drive the official WireGuard for Windows

The Windows agent does not carry its own tunnel code. It runs as a Windows service and uses the official WireGuard for Windows program that is installed on the computer:

- Install: WireGuard for Windows must already be installed. The agent installer checks and, if it is missing, stops with a plain message and a link (see the update below for why it does not install it).
- Tunnel: the agent writes the rendered config to a file and runs `wireguard /installtunnelservice <file>` to create the tunnel service (`WireGuardTunnel$<name>`), and `/uninstalltunnelservice` to remove it. To change a running tunnel it uses `wg syncconf`, so key and peer changes are applied without dropping the connection. Built as `internal/wg/wgapp.go` (`WireGuardApp`, a `wg.Backend`).
- Config files: the config holds the private key, so it lives in `C:\ProgramData\Wardline\tunnels`, a folder only the system account and administrators can read (set by the installer). Keys are never put on a command line. WireGuard's own DPAPI encryption only applies to files inside its own folder, so it is not used here; see `BLOCKED.md`. The private key is generated by the agent on the computer and is never sent anywhere (BUSINESS-RULES, agent device).
- Why: least code, the signed driver and its updates stay with WireGuard, and the person ends up with a standard, recognisable tunnel.

Sources read: the WireGuard for Windows enterprise documentation (command line switches, DPAPI config handling, MSI properties) and the wireguard-nt and embeddable-dll-service READMEs (the alternatives, not chosen).

### Update 2026-10-28: the installer does not download WireGuard
When I went to pin the installer by checksum, the SHA-256 for the amd64 MSI in WireGuard's signed `latest.sig` manifest did not match the file I downloaded from the same server, and I could not verify the signature in the container. So `wardline.exe agent install` only checks that WireGuard for Windows is installed and otherwise stops with a link. Bundling or fetching it is left for Dylan once the licence is checked and the signature can be verified.

### Open item: redistribution licence
The research did not find one statement covering redistribution of the official MSI. Dylan to confirm the licence text before any bundling is considered. Recorded in `BLOCKED.md`.

### Not chosen
- Embedding `wireguard-go` with the Wintun driver: we would ship and update the driver ourselves.
- Embedding the wireguard-nt tunnel DLL: most Windows-specific code, binary licence unchecked.

## Decision 2: installers published on GitHub Releases

Windows and Linux agent installers are built by `scripts/release.ps1` and attached to a GitHub Release. The web app links to them. This needs a GitHub repository for the project, which does not exist yet (`BLOCKED.md`). Until it does, builds stay local in `dist/`.
